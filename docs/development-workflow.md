# 개발과 긴급 수정

## 사용자가 기억할 말
- “개발판에 만들어줘”: dev에서 개발, 비공개 개발 사이트/Play 내부 테스트만.
- “공개판 긴급 수정”: 공개된 플랫폼별 기준 커밋에서 별도 핫픽스 작업. 해당 수정만 개발판에도 적용.
- “버전 N을 프로덕션으로”: 그 버전 검증 후 사용자가 명시한 대상만 공개. 일반적인 배포 요청으로 승격하지 않음.

## 핫픽스 절차
1. 해당 플랫폼의 실제 공개 버전과 소스 기준을 확인한다.
2. 그 커밋에서 별도 worktree 및 codex/hotfix-이름 브랜치를 만든다. dev의 미완성 기능을 가져오지 않는다.
3. 필요한 수정만 커밋하고 검증한다. 앱 신규 업로드 번호는 확인한 전체 최대 번호+1로 할당한다.
4. 내부 테스트로 전달한다. 같은 패키지의 테스터는 제공 가능한 가장 높은 코드로 업데이트될 수 있으므로 긴급판이 개발판을 덮을 수 있음도 확인한다.
5. 프로덕션은 사용자가 해당 버전을 명시해서 요청할 때만. 변경 커밋은 dev에 cherry-pick해서 재발을 막는다.
6. 공개 완료 후 플랫폼별 기준 기록을 갱신한다. main 정리는 웹 자동 배포 연결을 분리한 다음 별도 작업으로 수행한다.

## 개발 웹
별도 Sites 소유자 전용 사이트를 사용한다. 호스팅의 인증 경계가 접근을 제한하며 클라이언트 UID 배열로 보호하지 않는다. URL 비밀성에 의존하지 않는다.
준비 명령: `node scripts/prepare-private-dev.mjs C:/Users/Public/drawer-village-private-dev`.
이 명령은 정해진 dev 소스의 웹 자산만 복사하며 운영 config.js를 수정하지 않는다. 결제 및 Firebase 설정을 비우고 CSP로 운영 외부 API·외부 이미지·폼 전송을 차단한다. 저장은 별도 사이트 출처의 기기 저장소에 격리된다. 테스트 데이터는 실데이터의 자동 복제나 자동 병합 대상이 아니다.
현재 클라우드/멀티/로그인/구매 기능 시험은 지원하지 않는다. 이후 별도 Firebase 개발 프로젝트, 허용 사용자 규칙, 개발용 Functions, 결제 sandbox를 연결한 뒤 해당 테스트를 연다. 호스팅 preview 채널만 만들면 DB는 분리되지 않는다.

## 기능 스위치
개발 빌드의 DRAWER_FEATURES는 출시되지 않은 DLC를 기본 false로 둔다. 실제 신규 기능을 구현할 때 UI뿐 아니라 행동 계산·저장·마이그레이션 진입점도 스위치 경계로 분리한다. UI 스위치는 보안 또는 구매 권한이 아니다. 서버 권한은 별도로 검증한다. 스위치 변경은 데이터 마이그레이션을 되돌리지 못하며 번들 내 설정 변경은 앱 업데이트가 필요하다.

## 개발 순서
오류 안정화 → 개발/공개 데이터 분리 → 가구 시점·크기·앵커 규격 정리 → 작은 시뮬레이션 모듈과 회귀검사 → 첫 DLC의 작은 완결 기능 시험 → 내부 피드백 → 별도 출시 결정.
직업·재산팩은 후보로 두되 이 문서가 DLC 제작/가격 확정을 의미하지 않는다. 800명 처리 비용, Firestore 경합/읽기 비용은 실측 없이 가볍다고 판단하지 않는다.
